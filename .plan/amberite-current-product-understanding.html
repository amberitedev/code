Repository reality · Human understanding sheet

Amberite today, without the old roadmap.

Amberite is currently a Modrinth desktop client fork with a strong local client manager, a broad self-hosted server manager, and a real social foundation. The layer joining those parts into one simple multiplayer product is still unfinished.

Most accurate current framing

Working client and Copal server managers joined by real identity and social systems, with onboarding, collaboration authority, synchronization, remote access, and cleanup still in transition.

Assessment boundary

This describes what the repository expresses (not what the old document promises and not what deployed services were proven to run).

Inherited mature Modrinth behavior Connected meaningful Amberite flow Partial real parts, incomplete promise Residue mock, dev, dormant, or old surface
01 · Shape

Where product truth currently lives

Amberite AppThe user-facing shell, local launcher, library, account sidebar, discovery, and direct controller for one selected Core.
ModrinthThe external content catalog, project metadata, files, compatibility, and inherited creator/platform behavior.
Local app backendThe authority for client installations, Minecraft launching, local worlds, local files, and Minecraft accounts.
Copal CoreThe authority for self-hosted servers, runtime state, files, backups, server settings, members, roles, access, bans, invitations, and activity.
ConvexThe durable Amberite account, profiles, friends, blocks, social shell, pairing records, and minimal Core discovery data.
Realtime serviceAn optional online-presence overlay (it does not own friendships, permissions, Core health, or server state).
Intended boundary: the App discovers and selects a Core, then controls it directly. Convex should know only enough to connect authorized people; Copal should remain authoritative for the real server and its access rules.
02 · Changes

What Amberite has added to Modrinth

Connected

Amberite identity and friends

Minecraft-backed sign-in, Amberite profiles, friend requests, blocking, relationship-aware visibility, and an online/offline friends sidebar.

Connected

Self-hosted server management

Copal instances can be created and operated through status, console, content, files, backups, access, settings, logs, players, and maintenance systems.

Connected

Core setup and dashboard

The App can pair with an existing local or remote Core, then show overview, members, invitations, roles, and activity.

Connected

One library for several installation kinds

The Library combines local client installations, live Copal servers, and shared profiles, then separates them by purpose (modpacks, servers, custom, and shared).

Partial

Synced instances

A local client and Copal server can be presented as one dual-sided installation with shared profile and snapshot history, but full synchronization is not complete.

Partial

Groups and public profiles

User and group pages, members, roles, invitations, bans, Core association, privacy, and profile actions exist, but old and new authority models overlap.

Adapted

Hosting-shaped UX for Copal

Amberite reuses Modrinth’s server-management layouts for self-hosted servers, preserving familiar content, file, backup, access, overview, and settings patterns.

03 · Journey

The product path currently visible to a user

Sign inMinecraft identity becomes an Amberite account.
Pair CoreConnect to an already-running Copal installation.
Create serverChoose the Minecraft base and runtime settings.
Add contentUse the Modrinth catalog or local files.
Invite peopleManage friends, group membership, roles, and access.
Share clientExpose a synced profile for members to install (partial).
The strongest closed loop today: connect to Copal → create a server → install content → start it → manage its runtime and files. The friend-to-shared-client loop is present but does not yet close automatically.
04 · UX

What feels finished and what still feels like an alpha

Inherited and strong

Content discovery, project pages, compatible installation, local client instances, content management, local files, worlds, logs, skins, account switching, launching, and settings.

Amberite and usable

Core pairing, Core overview, server creation and power controls, console, Core content/files/backups, per-server access, friends, user profiles, group profiles, and the combined Library.

Product seams

First-run onboarding, Core installation, linked Modrinth identity, Core/group naming, invitations for new members, permission presentation, durable notifications, remote reachability, and Core online health.

Sync promise

Pairing a client with a server, publishing profile history, and installing an available shared archive exist; pulling changes, applying history, resolving conflicts, and reliably enforcing UI permissions do not.

Visible residue

Mock group links, a placeholder top-level Worlds screen, permanent Core development controls, local-only settings that look real, Modrinth-branded copy, and an old Hosting route outside normal navigation.

05 · Conflict

The main architectural mismatch

Groups and access currently have two live models. Convex still stores and changes the older friend-group membership, roles, invitations, and bans used by the desktop social UI. Copal separately stores the newer authoritative Core membership, custom roles, access, invitations, bans, and activity. Until one path owns each decision, the two views can disagree.

Convex view (social shell)

Useful for profiles, friends, group discovery, privacy, and a minimal list of Cores a user may reach.

Copal view (real authority)

Useful for actual server membership, instance access, roles, permissions, bans, invitations, and audit records.

Required final decision

Define whether a group is the social representation of one Core, a separate object, or something broader, then give every mutation one owner.

06 · Corrections

What the old Markdown gets materially wrong

Cloud backend
Convex plus a separate presence service replaced the Supabase direction.
Shared package
The active boundary is the TypeScript Amberite API package, not the planned Rust Amberite library.
Core name
Copal is the current name and the Core is much broader than the old issue list suggests.
Local setup
The App connects to an already-running local Copal; it does not yet install and start Copal for the user.
Synchronization
Profiles, manifests, snapshots, and archive engines exist, but they are not one automatic end-to-end system.
Remote access
Pairing and a published URL exist; managed server tunneling, domains, and universal remote connectivity do not.
Groups
They are not one settled system; the repository is migrating authority from cloud friend groups to Core-owned access.
Idea systems
Personal preferences, companion mod behavior, mod voting, failover hosting, and a complete remote dashboard are not current product capabilities.
07 · Next

Product decisions needed before the final Markdown

State the one primary promise Amberite must complete before every secondary feature.
Define the relationship between an Amberite user, friend group, Core, server, and synced profile.
Define exactly what “sync” guarantees and which side is authoritative for every kind of data.
Define the owner and member journeys from first sign-in through playing together.
Choose which inherited Modrinth platform, creator, Hosting, social, and server-directory surfaces remain visible.
Choose the supported connection promise for local network and remote friends.
Choose the permission model users see, then align the UI, Copal, and cloud projection behind it.
Draw the first release boundary so incomplete ideas cannot look like current commitments.
