# Amberite Repo Cleanup Plan - 2026-05-15

This plan exists to clean up the fork after the upstream diff audit. It is not
source of truth for the product; it is a cleanup direction based on the current
messy repo state.

## Goals

- Restore upstream Modrinth code where Amberite does not need to differ.
- Keep Amberite/Core behavior separate instead of patching shared code in-place.
- Preserve upstream style, structure, imports, naming, and component boundaries
	unless there is a clear Amberite reason to diverge.
- Make future upstream merges smaller and easier to review.
- Remove dead, risky, or local-only artifacts from tracked source.
- Fix Core/API/app contract mismatches before debugging UI symptoms.

## Main Problems Found

- Shared UI files were changed to behave like Core server pages, breaking normal
	Modrinth hosting assumptions and making upstream merges difficult.
- `/server/:id` and `/synced/:id` are unstable because route params, Core IDs,
	and sockets are captured once instead of reacting to route changes.
- Core instance creation is duplicated between Rust profile creation and frontend
	creation flow; `core_instance_id` edits are likely ignored by Rust `EditProfile`.
- Core, app, api-lib, and amberite-lib disagree on ports, routes, auth, relay IDs,
	and websocket flows.
- Supabase relay work is being replaced by Convex, so Supabase-specific relay/auth
	code should not be treated as the long-term architecture.
- Debug tooling, Storybook churn, planning docs, binary jars, and vendored patch
	trees added review noise and unrelated regressions.

## Immediate Cleanup Direction

1. Revert obvious unrelated damage.
2. Delete `apps/core/patches/swc_common-0.37.5/` and prevent it from coming back.
3. Restore shared `packages/ui` files close to upstream.
4. Move Core-specific UI into `packages/ui/src/.../core/` or another local `core`
	folder inside the existing UI package, not into a separate UI library.
5. Rebuild `/server/:id` and `/synced/:id` on top of forked Core-specific UI,
	not by replacing upstream hosting internals.
6. Fix Core/app/API contracts before deeper UI debugging.
7. Treat Deno removal as a later architecture project after the cleanup pass.

## Storybook Direction

Revert the current Storybook-related churn first, including broad autodocs,
docgen monkey-patches, large overview story catalogs, and script rename churn.
If `story` naming is still desired, reintroduce it later as a small deliberate
change, preferably with compatibility aliases or updated docs in the same patch.

## UI Library Direction

The UI library should remain one package. Do not create a separate Amberite UI
library. Instead, restore shared files and put Core-specific server-management
components in a dedicated `core` folder near the relevant server UI.

Acceptable changes to shared UI are small, standalone, and non-interfering, such
as a generic `TabGroup` if it is useful outside Amberite. Risky changes are those
that make shared components require `injectCoreClient()`, remove upstream
behavior, or change download/file/backup semantics for all consumers.

## Connection Architecture Direction

Amberite has four major pieces:

- Core: local/self-hosted server manager.
- API lib: typed communication layer used by app and web dashboard.
- App/web dashboard: frontend instance manager for Core.
- Convex: Supabase replacement, with backend logic in `.convex/` TypeScript.

API lib should expose three explicit communication modes:

- Direct HTTP/HTTPS: no relay; for live or non-critical operations like listing
	mods, requesting current state, reading logs, or console traffic.
- Core relay: Core stores important group-state messages locally and delivers
	them when the receiving side comes online. This supports communication when
	only one side is online.
- Convex relay: centralized always-delivered messages that must not depend on a
	Core being online, such as friend requests.

Auth is intentionally unsettled because Supabase is being replaced. Do not lock
new architecture to Supabase auth while Convex migration is planned.

## Core/API Contract Fixes

- Standardize the Core port and URL everywhere.
- Standardize route prefixes; current Core routes are not `/api/v1/*`.
- Pick one owner for Core instance creation.
- Persist `core_instance_id` in one reliable place.
- Align console websocket ticket flow.
- Align server properties key format.
- Add request timeouts and cancellation in api-lib.
- Defer or redesign relay behavior around Convex instead of fixing Supabase relay
	as the long-term path.

## Deno Direction

Delete the `swc_common` patch tree now. Broader Deno removal should be a later
architecture project. The likely replacement should be a stable, in-depth plugin
system that gives as much fork-like power as possible without the current Deno
complexity and vendored patch burden.

## Plan File Rules

Plans belong directly under `.plan/` using a name-date format. They are off-limits
to agents unless the user explicitly asks for a specific plan. A plan is a rough
planning artifact, not a reliable source of truth.
