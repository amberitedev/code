TL;DR and verdict

Verdict Not ready for an external alpha

The normal Core build is broken, all remote CI is blocked at checkout, and there are exploitable trust and authorization gaps.

Evidence-weighted readiness About 35–45%

This is alpha readiness, not lines-of-code completion. Feature breadth is much higher than release confidence.

Strongest area Core feature foundation

The direct integration harness passed 130 tests, and the backend covers most server management operations.

Largest risks Trust, authority, data, delivery

A malicious Core can receive an account JWT; permissions have split authorities; release and update systems still belong to Modrinth.

Recommended first alpha Focused server-manager slice

One owner, one directly connected Core, explicit networking, and a complete server/files/content/backup loop. Hide connected features until safe.

Rough order of effort 35–70 engineer-days

For the focused slice, after product decisions. A connected sync/social alpha adds roughly 15–30 engineer-days and more security review.

The project is not in a “polish-only” state. It has substantial product code, but current blockers include build failure, credential exposure, privilege escalation, possible destructive traversal, unsafe network exposure, unfinished sync, and a nonfunctional release path. UI polish belongs after those gates.

The shortest honest path forward

  1. Freeze new feature work and decide the alpha scope.
  2. Repair checkout, compilation, and required CI checks.
  3. Close trust, authorization, data-loss, and development-backdoor risks.
  4. Complete one clean-machine product loop on a deliberately narrow platform matrix.
  5. Own the Amberite identity, artifacts, configuration, privacy, and documentation.
  6. Run the release matrix, restore drill, soak test, and only then polish.

Recommended alpha definition

For this report, “alpha-ready” means the essential product loop works end to end on the supported platforms; failure and recovery paths are safe; security boundaries are real; installation and updates are honest; remaining work is optional feature breadth or UI refinement. A backend route or visible screen does not count as a finished feature until a user can complete it, receive useful errors, recover, and pass a test.

Focused alpha — recommended

  • A separately installed, documented Core on the selected host platform.
  • One owner connects and cryptographically verifies that Core.
  • Create, list, start, stop, restart, and delete a server.
  • Console, logs, content/mod management, files, and backup/restore.
  • Reconnect correctly after app/Core restarts and unexpected server exit.
  • Local/LAN or an approved encrypted overlay; no implicit Internet exposure.
  • Signed Amberite artifacts and manual update instructions, or an Amberite-owned updater.

Connected alpha — larger commitment

  • Everything in the focused alpha.
  • Core-authoritative members, roles, invites, bans, and ownership transfer.
  • Secure Convex projections and revoked access convergence.
  • Real synced-profile diff/apply/conflict/recovery behavior.
  • Optional realtime presence with Worker-runtime tests and supported origins.
  • Account deletion, credential rotation, retention, migrations, quotas, and cloud rollback.
Recommendation: ship the focused slice first. “Deferred” must mean feature-flagged or removed from alpha navigation and copy—not visible controls that silently do less than promised.

What is already good

Keep and harden

  • Core already covers instance CRUD/lifecycle, six loader families, console/RCON, files, content, logs, stats, players, backups, schedules, sync, roles, invites, activity, events, and diagnostics.
  • The Core integration suite meaningfully covers auth, object access, traversal, uploads, backups, and sync; 130 tests passed when the artifact was invoked directly.
  • Recent hardening includes atomic backup restore, SQLite foreign keys/WAL/busy timeout, many path/symlink guards, artifact hash verification, and stream permission rechecks.
  • The shared Amberite API has broad typed operations, central timeouts, safe error classes, and 60 passing pure tests.
  • Pairing/projection primitives use bounded codes, TTLs, random credentials, hash-only storage, constant-time comparison, revisions, and request-size limits.
  • Linked Modrinth tokens are AES-GCM encrypted and public Convex DTOs are generally redacted.

Product/UI foundation

  • The app reuses the established shared UI system and has credible loading, empty, offline, and error states on several main server screens.
  • Server list, runtime controls, console, files, content, backups, access, and activity have real Core-backed implementations—not only visual prototypes.
  • Amberite session tokens are stored in the OS keyring.
  • Native reveal/open helpers canonicalize and constrain paths.
  • Reduced-motion behavior already exists.
  • Most third-party GitHub Actions are commit-pinned; toolchains and lockfiles are pinned, and pnpm enforces a seven-day minimum package age.
  • The Copal workflow already models format/check/test, installer syntax, release version consistency, checksums, and packaging; it needs repair and proof, not replacement.
  • The realtime Worker has a sensible high-level model: short-lived single-use tickets, exact origins, JWT verification, HMAC-signed bridge calls, recent compatibility configuration, Durable Object migration, and observability.
Do not rewrite the product from scratch. Keep the shared UI, Core application/service separation, focused API client, and the documented Core/Convex/Worker authority model. The job is to make those boundaries true in code, delete legacy paths, and prove one loop—not to invent another framework or visual system.

P0 release blockers

These are grouped into workstreams rather than counting every symptom as a separate blocker. All must be closed, disproved by a regression test, or removed from the alpha surface.

P0-01 Make main checkout, compile, and run its real checks

Exactly four AGENTS files are committed with Git mode 120000 while their blobs contain document contents. Linux checkout fails before every workflow reaches its checks. Locally, Core has a moved-value compile error; Core clippy reports 16 errors; the desktop shell and API formatting checks also fail.

Evidence: AGENTS.md, apps/frontend/AGENTS.md, packages/api-client/AGENTS.md, packages/ui/AGENTS.md; apps/core/src/cli/admin.rs:275–296.

Done when

  • Every AGENTS document is mode 100644 and a fresh Linux clone succeeds.
  • Core check, format, clippy, library, and integration commands pass from clean CI.
  • App frontend, shell, API, Worker, and Convex have real required checks.
  • Main is protected only after the checks are green.

P0-02 Decide the visible alpha contract and hide everything else

Public paths currently expose mock groups, setup teleport controls, permission “view as” overrides, Synced promises, local-only settings, disabled macros, unimplemented networking, and overlapping server-management surfaces. This makes the product look more complete than it is and multiplies the security surface.

Evidence: apps/app-frontend/src/pages/Index.vue:131, pages/core/Index.vue:202, pages/instance/synced/SyncedIndex.vue:245, Core macros/network status handlers.

Done when

  • A one-page alpha product contract names supported and excluded features.
  • Excluded routes/actions are feature-gated or absent from production UI.
  • No alpha copy promises installation, sync, networking, or permissions that the code cannot deliver.

P0-03 Cryptographically authenticate Core before sending any credential

The connection check only asks an endpoint to echo a nonce and non-secret Core ID. The client can then retrieve and forward the full Convex account JWT; when the connected Core ID is absent, verification is skipped. A malicious URL can impersonate the Core and receive the token.

Evidence: packages/amberite-api/src/connection.ts:39–83, packages/amberite-api/src/client.ts:107–151, apps/app-frontend/src/core/connected-core.ts:72–80.

Done when

  • Pairing pins a Core public key or equivalent proof-of-possession identity.
  • The Core signs the nonce; the client verifies it before loading a token.
  • Core receives a short-lived, audience/Core-scoped token—not the general account JWT.
  • Non-loopback authenticated calls require HTTPS or an approved encrypted overlay.
  • A malicious echo-server regression test proves it receives no Authorization header.

P0-04 Make Core the only authority for roles, access, invites, bans, and ownership

Desktop flows still mutate deprecated Convex friend-group state while Core owns real access. Core removals may not revoke cloud sync access, Convex kicks may not revoke Core, and the server UI currently grants the user 0xffff permission bits. Synced permissions derive from a social group role.

Evidence: apps/app-frontend/src/composables/useSocial.ts:372–390, convex/friendGroups.ts:206–278, convex/sync.ts:55–235, packages/ui/src/layouts/wrapped/hosting/manage/use-core-server-runtime.ts:294.

Done when

  • Every membership/role/invite/ban/ownership action calls Core.
  • Legacy public Convex authority mutations are removed or unreachable.
  • UI capabilities come from an authenticated Core response.
  • Revocation removes Core and cloud access in one explicit E2E test.
  • Outsider invite acceptance uses identity without requiring prior membership.

P0-05 Repair identity, block, ownership, and credential invariants

Admins can invite a new owner; blocking leaves pending requests that can later recreate friendship; live scope ignores blocks; “delete account” only writes a timestamp; ownership transfer/unlink does not consistently rotate or revoke Core projection credentials.

Evidence: convex/groupInvites.ts:13–106, convex/friends.ts:185–241, convex/social.ts:180–195, convex/auth.ts:162–171, convex/coreProjection.ts:73–85.

Done when

  • Only the canonical ownership-transfer flow can create an owner.
  • Block atomically cancels requests/friendship and is rechecked at every interaction.
  • Account deletion revokes sessions, rejects sign-in, handles PII/tokens/ownership, and follows a documented retention policy.
  • Transfer/unpair rotates credentials; old secrets immediately receive 401.
  • Server-side adversarial tests cover direct raw calls, not only UI paths.

P0-06 Make Core networking explicit, constrained, and encrypted

Core serves plain HTTP, public URL validation is weak, and a GET to /network/status creates a one-hour UPnP mapping for the management API. The desktop accepts arbitrary Core origins while Tauri only permits localhost, Convex, and one personal Tailscale suffix.

Evidence: apps/core/src/application/network_service.rs:41–101, apps/app/capabilities/plugins.json:24–74, apps/app/tauri.conf.json:116.

Done when

  • Alpha networking matrix is explicit: loopback, LAN, approved overlay, and/or public HTTPS.
  • GET is read-only; UPnP is explicit opt-in, auditable, and cleaned up.
  • Remote management has a supported TLS/proxy/tunnel path and strict URL validation.
  • Tauri capabilities match the supported model without a developer’s private tailnet.

P0-07 Prevent destructive navigation, traversal, and lifecycle races

Opening Library or an instance can silently delete legacy server profiles. Core installation IDs appear to be joined into paths without strict validation and deletion removes the filesystem first. Only start uses the per-instance lock; delete, restore, repair, version change, and sync can race with live operations.

Evidence: apps/app-frontend/src/pages/library/Index.vue:64, pages/instance/InstanceRouter.vue:37, apps/core/src/application/installation_service.rs, Core lifecycle/backup/sync services.

Done when

  • Page navigation never performs destructive migration.
  • Legacy migration is explicit, backed up, idempotent, cancellable, and recoverable.
  • Installation IDs reject separators/dot segments and canonical containment tests preserve sentinel data.
  • One operation lock/state machine covers every destructive lifecycle mutation.
  • Deletion is rollback-safe and exposed in the desktop with a clear data-retention choice.

P0-08 Make uploads, archives, and server content safe at real sizes

Core does not configure Axum multipart limits, leaving essential mod/modpack uploads at the 2 MB default. Several paths buffer full files; archive entry count/decompressed size are not bounded. Minecraft jars/mods also run with Core’s OS identity and can access Core secrets and other instances.

Evidence: Core router/upload/mod/modpack/archive handlers; no DefaultBodyLimit override; Core process spawning model.

Done when

  • Per-route limits support realistic files and reject oversized bodies with 413.
  • Uploads stream to temporary storage with interruption cleanup and bounded memory.
  • Archive count/expanded-size/ratio limits are tested.
  • Alpha explicitly restricts installs to a trusted owner, or instances are OS/container isolated.

P0-09 Provide one honest, working Core distribution and onboarding path

The UI says it will download/install Copal but only probes localhost. There are no releases, both Copal npm packages return 404, the curl installer cannot find a release, and its generic “latest release” lookup can select an app release. The Docker build context cannot include the Core’s Daedalus path dependency, and its runtime has no Java or Minecraft port plan.

Evidence: components/core/stages/StartStage.vue, use-core-onboarding-state.ts:158, apps/core/scripts/install.sh:26–40, apps/core/Dockerfile, apps/core/Cargo.toml:140.

Done when

  • Decide managed sidecar versus separately installed Core; make copy and UI match.
  • Publish versioned, checksummed artifacts for a declared Core platform.
  • Installer selects Copal tags explicitly and passes a clean-host smoke test.
  • If Docker is supported, a real container creates, starts, pings, and stops one certified server.

P0-10 Finish Synced end to end or remove it from alpha

The product promises synchronized client/server profiles, but current behavior publishes manifests/snapshots/events as “planned” without a complete pull/apply/reconcile/conflict/ restore path. Creation is non-transactional and can orphan a Core instance; registration failures are suppressed. Synced network controls still call Modrinth Archon.

Evidence: convex/sync.ts:167–205, pages/instance/synced/SyncedSync.vue:119, providers/setup/creation-modal.ts:171, pages/instance/server/settings/pages/network.vue:222–288.

Done when

  • Focused alpha: all Synced creation/navigation/actions are hidden and data is preserved.
  • Connected alpha: conflict policy, CAS/locking, retry/rollback, quotas, and multi-device convergence pass E2E.
  • No Core page calls an unrelated hosted-server backend.

P0-11 Own the app identity, production configuration, release, and update path

The app build copies a production env with empty VITE_CONVEX_URL, empty realtime URL, and no required VITE_CONVEX_SITE_URL; Vite hard-fails. Core production CONVEX_URL is empty. App updater key/endpoint, release filenames, bucket URL, workflow names, and deep-link scheme remain Modrinth. The release job lacks content-write permission under current repository defaults. With no tag, the build’s raw commit-hash version fallback is not valid Cargo SemVer, and artifact upload globs match Modrinth App_* even though Tauri now produces Amberite-named bundles.

Evidence: packages/app-lib/.env.prod:9–11, apps/app-frontend/vite.config.ts:14–49, apps/core/.env.prod:8, apps/app/tauri-release.conf.json:31–35, .github/workflows/theseus-release.yml:24–159.

Done when

  • Permanent reverse-DNS bundle ID, Amberite URL scheme, names, icons, descriptions, and version policy are chosen.
  • Production/staging templates validate all public config without committing secrets.
  • A valid SemVer tag—not the current raw commit-hash fallback—drives package versions.
  • Selected platforms produce signed Amberite artifacts from a tag, and upload globs match Amberite bundle names.
  • Updater is Amberite-owned and upgrade-tested, or disabled with a documented manual path.
  • Release permissions, artifact upload, manifest, rollback, and smoke check are proven in a dry run.

P0-12 Remove restricted upstream branding and make privacy/legal behavior truthful

The repository’s own copying rules require forks to remove Modrinth branding, but app icons, DMG art, covers, UI copy, support/legal/security pages, updater, and deep links remain. The saved telemetry preference defaults on and the app embeds a Modrinth PostHog project/key/host. A normal packaged Tauri hostname likely hits the localhost guard unless explicitly enabled, so actual sending was not proven. Sentry can initialize before the saved telemetry preference is consulted. Core/API/ realtime license coverage is unclear.

Evidence: COPYING.md:7–21, apps/app/icons, apps/app/dmg/dmg-background.png, helpers/analytics.ts:59–78, packages/app-lib/migrations/20240711194701_init.sql:13, components/ui/settings/PrivacySettings.vue:39–46.

Done when

  • Restricted Modrinth assets/marks and misleading links are removed from the fork and artifacts.
  • Optional telemetry defaults off, is Amberite-owned, is gated before initialization, and has an accurate policy.
  • Privacy, terms, security contact, support, licenses, notices, and data-deletion policy are published.
  • Shipped dependency tree has zero unaccepted critical advisories; the critical PostHog/protobuf path is upgraded or removed.

P0-13 Remove production development backdoors and disable stale upstream automation

Core debug builds accept predictable dev:<id> ownership and expose an unauthenticated pairing reset. Convex dev mode accepts __actAs and exposes destructive reset/state functions if one environment flag is wrong. The desktop dev persona is not compile-gated. The inherited frontend deployment workflow can target Modrinth domains and Cloudflare/Sentry resources without an Amberite owner guard.

Evidence: Core auth/setup extractor/config, convex/_socialRules.ts:63–70, convex/dev.ts:37–115, apps/app/src/api/auth.rs:52, .github/workflows/frontend-deploy.yml, apps/frontend/wrangler.jsonc.

Done when

  • Dev/no-auth requires explicit random local authorization and refuses non-loopback bind.
  • Production cannot activate dev impersonation/reset code; deployment fails closed.
  • All mock/teleport/view-as controls are compile- or feature-gated out.
  • Upstream deploy/release workflows are disabled or rebuilt for Amberite before checkout is repaired.

P0-14 Prove the clean-machine essential loop

There is no behavioral UI/shell suite and no current packaged runtime proof. An alpha cannot be declared from static routes, typechecks, or a manually invoked backend artifact.

Done when

  • A clean supported host installs Core and a clean supported desktop installs Amberite.
  • The user connects/pairs, creates a certified server, starts it, joins/pings it, uses console, installs content, edits a file, backs up/restores, stops, and deletes it.
  • App/Core restart, offline Core, failed install, disk pressure, corrupt backup, unauthorized user, and update/rollback cases are exercised.
  • Evidence is recorded in CI artifacts or a signed release checklist.

Decisions required before more implementation

Resolve these in writing. Otherwise the team will keep implementing competing assumptions and create more rework.

ID Decision Recommended alpha choice Why it matters
D-01 Focused or connected alpha? Focused first. Removes the least mature and most security-sensitive sync/social/presence work from the first external gate.
D-02 Who installs/manages Core? Separately installed Core for the first alpha, unless managed lifecycle is a defining promise. Current UI promises management it does not implement; cross-platform sidecar lifecycle is a separate product.
D-03 Supported platform matrix? One desktop OS/arch plus Linux x64 Core first; expand only after proof. No platform currently has a successful packaged Amberite build, while Copal distribution only targets Linux x64.
D-04 Supported network topology? Loopback/LAN or explicitly approved encrypted overlay; no public plain HTTP or automatic UPnP. Defines Tauri scopes, TLS, identity, threat model, support burden, and copy.
D-05 Authorization owner? Core is sole authority; Convex gets only minimal projection. This is already the documented architecture and avoids contradictory access state.
D-06 Does Synced ship? Hide in focused alpha. Publishing metadata is not synchronization; conflict and rollback semantics are product decisions.
D-07 Does realtime presence ship? Defer; durable social state/direct Core control do not depend on it. The architecture is promising, but runtime tests/origins/cleanup are unfinished.
D-08 Content trust model? Trusted owner-only installs for alpha, clearly documented. Delegated untrusted content requires OS/container isolation to protect Core and other instances.
D-09 Certified loader matrix? Start with a small tested subset such as Vanilla, Paper, and Fabric. Six nominal loaders create a large install/Java/version compatibility matrix.
D-10 Backup guarantee? Define RPO/RTO, local/offsite scope, DB/config coverage, retention, and restore ownership. “Backup exists” is not the same as a tested recovery guarantee.
D-11 Telemetry/support vendors? Default optional telemetry off; use Amberite-owned endpoints/policies only. Current behavior sends to Modrinth and conflicts with the privacy copy and fork obligations.
D-12 Stable identity/version? Choose an owned reverse-DNS bundle ID, amberite://-style scheme, and 0.x.y-alpha.n policy before installs. Changing bundle ID/data paths/update keys after testers install creates migration debt.
D-13 Inherited Modrinth surfaces? Keep content API compatibility where licensed/required; hide/remove hosted billing, ads, Plus, support, and upstream deploy surfaces. The inherited app is an implementation base, not automatically part of Amberite’s product promise.
D-14 Minecraft EULA flow? Explicit user acceptance with auditability. Automatic eula=true is a product/legal choice, not an invisible implementation detail.

Test and quality strategy

The target is not maximum coverage. It is reliable evidence around destructive, privileged, and cross-process behavior. Put tests at the authority boundary where a regression can cause credential loss, data loss, or a stranded server.

Layer Minimum alpha suite CI placement
Core unit/integration Auth/authz, traversal, lifecycle concurrency, upload/archive limits, install/loader, process crash, backup/restore, migration, permissions. Linux required; no real router mutation; explicit fixtures.
API contract Producer/consumer DTO validation, malformed REST/SSE/WS, timeout/error codes, protocol compatibility, malicious Core handshake. Pure tests plus explicit non-hidden Core fixture job.
Convex security Direct mutation tests for owner invite, blocks, deletion, credential rotation, projection revocation, redaction, sync visibility, rate limits, migration. Required cloud/backend job.
Worker runtime Real Vitest Workers pool: JWT, exact origins, single-use ticket, hibernation, alarm order, cleanup pagination, fan-out, invalidation, deployment reconnect. Required only when presence is enabled.
Desktop component Onboarding, creation, lifecycle pending/errors, destructive confirmation, permission visibility, offline/reconnect, telemetry preference. Fast per-PR behavioral tests.
Packaged E2E Clean install, Core connect, create/start/join/console/content/files/backup/restore/delete, restart, update. Nightly/release matrix on certified platforms.
Fault/destructive Disk full, network loss, corrupt archive/backup, process crash, double click/concurrent operations, partial cloud failure, stale credential. Nightly/release; artifacts retained.
Release/security Fresh checkout, signed artifact verification, dependency/license/secret scan, config preflight, updater/manual migration, rollback. Required tag/release workflow.
